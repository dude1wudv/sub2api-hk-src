> 更新日期：2026-09-05。

> Fork：https://github.com/higfy5/sub2api-hk-src （已通过 GitHub API 核验 Fork 关系）。

本文件更新原有视觉提案，作为本次优化的唯一主计划。保留已有暖纸主题方向，扩展到交互流畅度、操作流程、反馈与恢复。旧计划中的组件数量、色值数量、特定模型协作方式和工作区状态不作为本轮依据。

**实施范围覆盖说明（优先于下文原计划）**：用户后续要求“主要优化交互界面的视觉感受”，并排除支付与后台用户管理。本次只做现有暖纸视觉的共享控件、布局、浅暗色、窄屏、弹窗和状态反馈优化，以及密钥接入、用量、渠道账户和排障的相关小改动。原计划中的支付流程、用户管理、监控虚拟化、新接口与分包调整不在本 PR 实施范围。共享主题/组件的统一样式会自然影响其调用页面，但不修改被排除页面的专用代码和业务语义。

## 1. 目标与范围

目标不是换皮，而是让用户更快完成任务、理解系统状态，并在失败后知道如何继续。

| 对象 | 高频任务 | 优化目标 |
| --- | --- | --- |
| 新用户 | 登录、创建 API Key、配置客户端、首次调用 | 下一步明确，减少在引导、密钥、模型和用量页之间往返 |
| 日常用户 | 查看额度、查询用量、管理密钥、充值/订阅 | 刷新不中断阅读，费用与状态可解释，失败可恢复 |
| 管理员 | 筛选账户、批量操作、发现异常、排障 | 保持筛选上下文，明确操作范围与结果，降低误操作 |
| 移动端/键盘用户 | 完成以上核心任务 | 关键操作不被隐藏、遮挡或困在不可访问的浮层中 |

### 实施边界

- 保留 Vue 3、TypeScript、Vite、Tailwind、Pinia、vue-i18n 和现有通用组件；不重写技术栈、不另建组件库。
- 可以调整前端信息层级、流程编排、加载状态和请求生命周期；不改变后端计费、授权、订单终态及 API 语义。
- 复用现有路由、引导、剪贴板、表格和缓存逻辑，改动共享接口时迁移全部调用方。
- 不默认增加全局状态管理框架、请求缓存库、命令面板或新的监控服务。
- 不触碰生产凭据，不执行真实支付、批量删除或账户停用来验证体验。
- 涉及新接口能力的建议必须先完成接口核对，单独列出依赖，不用前端假状态代替后端能力。

## 3. 产品与视觉方向

延续“暖纸底色 + 陶土主行动 + 冷蓝链接”，以清晰、克制、数据优先为原则。

### 信息层级

- 用户概览优先回答：现在能否使用、剩余多少、近期花费、下一步做什么；复杂趋势放到次级区域。
- 每页一个主要行动，次要操作弱化；删除、停用等危险操作与主要行动分离。
- 侧栏按任务分组，保留权限、功能开关、自定义菜单与原有深链接；调整名称时同步翻译和引导定位。
- 用户端与管理端保持同一控件语言，但允许管理端更高信息密度。

### 设计规范

| 项目 | 建议规范 | 验收 |
| --- | --- | --- |
| 表面层级 | 复用 canvas、surface、surface-2、surface-elevated | 浅暗色均能区分页面、卡片、输入和浮层 |
| 颜色 | 品牌、链接、成功/警告/错误、分类色分工 | 状态带文字或图标，图表不只依赖颜色 |
| 排版 | 4/8px 间距节奏；金额/计数用等宽数字；长标识可完整查看和复制 | 中英文、长模型名、长 Key、200% 缩放不遮挡关键动作 |
| 控件 | 沿用现有约 8px 控件、12px 卡片/浮层圆角；统一高度和对齐 | 同类控件 loading/error/disabled/focus 反馈一致 |
| 数据密度 | 桌面普通行以 40–44px 为候选，复杂内容按需增高；移动触点优先 44px | 不以固定行高截断错误、额度或操作 |
| 动效 | 控件约 120–180ms、浮层约 180–220ms；只用于反馈因果 | 不动画布局尺寸和大面积模糊；减弱动画模式取消非必要位移 |
| 可访问性 | 普通文字对比度 ≥4.5:1，大文字 ≥3:1，关键非文本状态 ≥3:1 | 焦点可见，键盘完整通行；读屏可获取状态更新 |

以上数值是设计目标，不是对现有实现的测量结果。先在登录、Keys、Accounts 三个真实页面验证，再推广。

## 4. 优化工作包与优先级

P0 为首轮必做的体验可靠性与基线，P1 为高频效率和视觉一致性，P2 为后续低频覆盖。优先级不代表已确认的故障严重级别。

### P0-A：加载、刷新与请求一致性

主要位置：`frontend/src/components/common/DataTable.vue`、`frontend/src/composables/useTableLoader.ts`、`frontend/src/views/user/UsageView.vue`、`frontend/src/views/admin/AccountsView.vue`。

- 区分首次加载、同条件后台刷新、切换查询、空结果、失败五种状态。
- 首次加载使用稳定尺寸骨架；同条件刷新保留现有行，显示轻量“更新中”和最后更新时间。
- 切换筛选时明确显示新条件加载中；若暂留旧数据，必须标记“上一查询结果”，避免用户误操作。
- 同条件刷新失败保留可读数据并标明过期，提供就地重试；真实空结果提供清除筛选入口。
- 复用取消请求与 generation/序号保护；成功、错误、loading 的提交均须属于当前查询。
- 更新中的旧结果不得被误当作当前筛选批量操作对象；筛选变化时明确清除或重新确认选择。

验收：人为让旧请求晚于新请求返回，最终列表、统计、错误提示均对应新条件；自动刷新不重置滚动；断网不把历史数据变成“没有数据”。

### P0-B：操作反馈与弹窗安全

主要位置：`frontend/src/components/common/BaseDialog.vue`、`frontend/src/components/common/ConfirmDialog.vue`、`frontend/src/components/common/Toast.vue`、密钥及支付相关页面。

- 优先补齐共享弹窗 Tab/Shift+Tab 焦点圈定、仅顶层处理 Escape、多浮层滚动锁与焦点恢复。
- 提交按钮就地反馈、防重复触发；校验信息贴近字段，失败保留非敏感输入。
- 复制成功在触发处短暂反馈，同时支持读屏；复制失败给可选中文本，不虚报成功。
- 删除、停用、批量变更显示对象、范围、影响；只有服务端确认后显示成功。
- 资金、密钥创建、删除、权限变更不使用未经确认的乐观成功状态，也不自动重试非幂等写入。

验收：仅键盘完成打开、编辑、提交与关闭；嵌套弹窗关闭只影响顶层；连续点击不会产生多个前端提交；后端错误可见且可恢复。

### P1-A：新用户接入闭环

目标流程：登录 → 概览中的接入任务 → 创建 Key → 同一上下文获取 Base URL/客户端配置 → 用户主动发起调用 → 用量页查看结果。

- 复用现有 Tour，增加明确的任务完成状态和继续入口；可跳过、稍后继续，不强制遮罩挡住老用户。
- 创建 Key 表单先呈现必需字段；高级额度、限制等逐步披露，但不可隐去影响可用性或计费的默认值。
- 创建成功后提供“复制 Key / 查看接入示例 / 查看用量”连续动作；不重新寻找说明入口。
- 客户端配置按现有支持范围提供；示例默认使用占位符，只有用户明确操作才复制真实 Key。
- 不将密钥放进 URL、分析事件、持久化草稿或截图；不会因进入引导自动执行计费 API 调用。
- 首次调用成功状态必须来自后端可验证记录；若现有接口不足，保留“查看调用记录”而非伪造检测。

验收：同一新人任务相比基线，跨页往返和操作数不增加；目标将完成时间中位数降低至少 20%，以可重复可用性测试确认。

### P1-B：用量、额度与付费流程

主要位置：`frontend/src/views/user/DashboardView.vue`、`frontend/src/views/user/UsageView.vue`、`frontend/src/views/user/PaymentView.vue`、`frontend/src/views/user/SubscriptionsView.vue`。

- 概览突出当前可用额度、订阅有效期、最近消费及相关操作；余额与订阅额度不能混成一个无法解释的数。
- 用量页保持日期、筛选和返回上下文；列表、汇总、图表使用同一查询口径，部分失败分别提示。
- 显示时区、币种、计费单位与关键口径；错误记录就近连接已有详情，不要求用户在多个页面手工重找。
- 购买页按“选择金额/套餐 → 查看费用与限制 → 支付 → 结果与继续使用”组织，复用现有订单和支付组件。
- 清晰区分等待付款、处理中、成功、失败、过期；离开后可从已有订单入口恢复，不默认重复建单。
- 订单终态以服务端为准；前端超时或支付 SDK 返回不直接代表到账成功。

验收：刷新支付结果页、关闭后返回、支付失败、订单处理中均有明确状态与下一步；只使用沙箱验证，不产生真实扣款。

### P1-C：管理端批量操作与排障

主要位置：`frontend/src/views/admin/AccountsView.vue`、`frontend/src/views/admin/UsageView.vue`、`frontend/src/components/layout/TablePageLayout.vue`、`frontend/src/features/channel-monitor-v2`。

- 明确显示已选数量、选择范围和批量动作；翻页/改筛选时不能让用户误以为“当前页”就是“全部结果”。
- 批量操作遵循“选择 → 影响确认 → 执行反馈 → 成功/失败明细”；已有结果能力直接复用。
- 仅当服务端返回可靠的逐项结果且语义允许时，提供失败项重试；否则提供失败列表与人工处理入口。
- 保留常用筛选、排序、页大小和返回上下文；URL 只放可公开分享的非敏感查询参数。
- 异常状态展示原因、时间和已有处理入口；排障跳转携带非敏感账户/时间筛选，不凭空创建无法支持的跨页关联。
- 现有虚拟化和 Sticky 保留，行高、展开详情、移动布局调整后专项验证；性能瓶颈未证实前不重写大页面。

验收：100 条账户场景可完成筛选、选择、批量反馈和返回；部分失败不展示全成功；删除末页最后一项后分页有效。

### P1-D：运行性能与视觉收敛

- 对生产构建测量入口依赖，再决定是否把 xlsx 从常用 vendor-ui 中拆出并延迟到导出动作加载。
- 检查图表、支付 SDK、编辑/导出组件的实际加载时机；已按需加载的能力不重复改造。
- 在现有预加载中按用户角色、节流/省流量条件约束范围；不在弱网无条件抢占主请求带宽。
- 页面隐藏时暂停非必要刷新，返回时按缓存新鲜度更新；交易相关状态遵守现有支付语义。
- 统一应用框架、基础表单、状态、卡片与表格视觉；保留 Token 单一来源，不积累页面级覆盖层。
- 先覆盖登录、用户概览、Keys、Usage、Accounts，再扩展其他模块；不为视觉改造破坏现有 data-tour、权限或自定义菜单。

验收：性能达到第 6 节预算；浅暗色、窄屏和缩放均通过；无首屏体积无依据增长。

### P2：低频页面与一致性补齐

覆盖设置、个人资料、兑换、模型广场、首页、公共页面与低频管理页。优先解决状态缺失、长内容溢出、表单恢复和操作分组，再处理装饰细节。不把整站换色作为前置条件，不增加与任务无关的动画。

## 5. 交付顺序与依赖

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0 基线 | 核心流程录屏/步骤表、浅暗截图、生产包依赖与性能记录、问题分级 | 能复现、能比较；确定首批实际问题与接口边界 |
| M1 可靠交互 | P0-A/P0-B；以 Keys、Accounts 验证共享组件；视觉规范在样板页定稿 | 请求乱序、断网、键盘/浮层、选择范围场景通过 |
| M2 用户高频闭环 | 接入任务、密钥成功后动作、用量与付费反馈 | 新人接入和沙箱支付可端到端完成，核心操作步数不增加 |
| M3 管理效率 | 批量操作结果、异常排查、筛选上下文、密集数据视觉 | 批量部分失败、返回定位、滚动与移动操作通过 |
| M4 全站一致性 | 按测量落实分包/预加载，覆盖低频页，完成验收矩阵 | 性能、视觉、可访问性、业务回归达标 |

依赖关系：M0 → M1 → M2/M3 → M4。M2 与 M3 可在共享交互契约冻结后并行；全局主题、DataTable、BaseDialog 由同一集成负责人管理，避免并发改同一基础组件。

职责：产品/设计负责任务路径与视觉取舍；前端负责实现及浏览器证据；后端仅核对接口语义与沙箱能力；验收负责人统一检查跨页流程。人员可兼任，不绑定具体 AI 模型。

首批实施清单：

1. 记录登录 → Keys → 配置示例、筛选 → 详情 → 返回、批量部分失败、沙箱支付恢复四条流程基线。
2. 复现 DataTable 后台刷新与 BaseDialog 嵌套焦点行为。
3. 确定首次加载/刷新/错误和批量选择范围的统一契约。
4. 在现有暖纸 Token 上验证三张代表页，不直接改首页或全站配色。
5. 产出首批浏览器前后对比证据，通过后推广。

## 6. 验收指标与测量方法

以下均为目标，当前值待 M0 测量；不得宣称已经达到或已经提升某百分比。

### 性能预算

| 指标 | 目标 | 测量口径 |
| --- | --- | --- |
| 点击到视觉反馈 | p95 ≤100ms | 同机同浏览器，重复核心动作至少 30 次；只计前端反馈，不把 API 完成时间算入 |
| 已加载路由切换到可操作框架 | p95 ≤300ms | 同主题与数据集；新数据加载另行计时，不能以空框架声称整个页面就绪 |
| LCP / CLS | ≤2.5s / ≤0.1 | 生产构建、固定移动模拟设备、固定网络/CPU节流；冷/热缓存分开，至少 5 次记录中位数与范围 |
| INP | 真实用户 p75 ≤200ms | 若无合规真实用户数据，只报告实验室交互耗时，不能伪称现场 INP 达标 |
| 密集列表 | 连续滚动无空白、位置跳变与可感知长卡顿 | 实际分页上限及 100/1000 行组件压力场景；桌面与移动分别录制 Performance trace |
| 首屏 JS | 相对基线不增加超过 5%，超出须说明必要性 | 比较相同入口首次实际下载的压缩字节，不仅比较单个 chunk 大小 |
| 请求行为 | 同条件刷新不重复并发；旧响应不覆盖新条件 | 注入网络延迟/乱序；测试脚本只作用于测试环境 |

生产构建输出到 `backend/internal/web/dist`（见 `frontend/vite.config.ts:106-108`），测量应在隔离工作树/构建环境进行，避免把构建产物误提交为前端源码变更。Vite 开发模式会向后端读取公开配置，不能把开发服务器的首次等待作为线上性能结论。

### 使用体验验收

- 核心任务完成率不得低于基线；由至少 5 名未参与实现的目标用户使用同一任务脚本测试，报告成功数与失败原因，不将小样本包装成统计结论。
- 新用户接入时间中位数目标降低 ≥20%；同时记录点击数、跨页次数和求助次数，不为了少点击而隐藏关键确认。
- 管理排障与批量处理操作步数不增加；若基线暴露明显重复往返，优先降低至少一次往返。
- 首次使用、已有数据、空结果、加载失败、部分失败、权限不足、会话过期分别有明确解释和下一步。
- 任何计费、权限、选择对象不一致属于阻断发布问题。

### 视觉与输入矩阵

- 视口：360×800、768×1024、1440×900、1920×1080。
- 主题：浅/暗；语言：简体中文/English；缩放：100%/125%/200%。
- 浏览器：Chromium 与 Firefox 桌面、Safari/iOS 核心路径；无相应设备则记录未验证，不冒充通过。
- 状态：默认、悬停、聚焦、禁用、提交、首次加载、刷新、空、错、部分成功。
- 输入：鼠标、键盘、触控；抽查读屏；移动键盘弹出后提交按钮仍可到达。
- 每个高频页面验证自身关键组合；不要求全部低频页穷举无意义的笛卡尔积。

## 7. 实施验证、发布与风险控制

### 验证方式

先跑真实场景再谈指标：浏览器录屏/截图、Network 与 Performance 记录、任务完成路径是主要证据。计划阶段不运行无关测试，也不把源码扫描冒充视觉验证。

实施后的既有检查命令：

```bash
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend run typecheck
pnpm --dir frontend run lint:check
pnpm --dir frontend run build
make test-frontend-critical
```

`make test-frontend-critical` 已在根目录 Makefile 定义；无 make 的环境按该目标列出的文件运行 `pnpm --dir frontend exec vitest run ...`。测试在相关批次完成后统一运行，不在并发编辑期间反复执行全套。

永久回归用例只保留真实边界：乱序响应、会话失效、嵌套弹窗焦点、批量部分失败、支付恢复等。纯视觉调整以实际页面验证为主，不新增断言 CSS 字符串或组件内部结构的脆弱测试。

### 发布与回退

- 每批独立提交，附影响页面、前后证据、检查结果；本轮计划文档不自动提交、推送或部署。
- 先测试环境、再受控发布；前端静态资源与后端嵌入版本配套，不能仅替换部分 chunk。
- 旧路由深链接、权限守卫、翻译键、引导定位与已有浏览器偏好必须继续有效；格式确需改变时完成一次性迁移。
- 基线以上的误操作、计费展示错乱、核心任务阻断、显著性能回退即停止扩散并回退该批版本。
- 不长期维护两套组件或用隐藏开关遗留旧逻辑；迁移验证完成后移除被替代的样式/逻辑和临时测量文件。

### 主要风险

| 风险 | 控制 |
| --- | --- |
| 共享组件影响大量页面 | 先代表页，后调用方逐项迁移，再推广 |
| 密集表格更紧凑却更难操作 | 允许内容自适应高度，验证虚拟化与移动触控 |
| 保留旧数据让用户误认为已更新 | 显式标注更新/过期/上一查询状态，约束批量动作 |
| 支付、密钥“看似成功”但实际失败 | 服务端确认为准；避免非幂等请求自动重试 |
| 缓存/预加载带来隐私或额外网络消耗 | 按账号/角色隔离，登出清理，弱网节制；不持久化敏感值 |
| 仅为漂亮牺牲对比度与速度 | 真实页面对比度、低端设备与减弱动画作为门禁 |
| 无测试账号或支付沙箱 | M0 列为对应流程依赖；先完成无需该依赖的组件和公开页面验证，不伪造端到端结论 |
